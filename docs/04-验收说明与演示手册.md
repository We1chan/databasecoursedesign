# 终期验收说明与演示手册

课程安排在数据库优化与业务测试后进行终期验收。本阶段以答辩汇报、数据库复验和提交材料核对为交付内容。汇报中的实测数字以仓库日志为准。

## 1. 汇报顺序

[教务系统数据库终期验收汇报](04-教务系统数据库终期验收汇报.pptx)共 12 页，每页附有 PowerPoint 演讲者备注。按约 8–10 分钟组织，可根据现场分配的时间调整演示长度。

| 页码 | 讲解重点 |
|---|---|
| 1–2 | 需求、三类角色与五个业务模块，用选课记录说明模块之间的数据关系 |
| 3–4 | 从概念结构转成 MySQL 关系模式，解释历史快照与约束的责任 |
| 5–7 | 讲清最后一个名额、成绩发布与更正，再补充导入、排考及评教的实际例子 |
| 8–10 | 汇报 15 个通过的场景，再用待办查询前后的执行计划和耗时说明优化 |
| 11–12 | 运行两条代表性业务链路，说明测试边界和提交材料 |

## 2. 现场演示

### 2.1 准备

在仓库根目录运行，使用 Python 3.11 或以上版本和供测试使用的 MySQL 8.0 实例。业务套件会自行创建、初始化和清理临时库，连接账号须能创建这些临时库。下面的端口为示例值，连接参数按现场测试实例填写。

```powershell
python -m pip install -r tests/requirements.txt
$env:DB_TEST_HOST = '127.0.0.1'
$env:DB_TEST_PORT = '43684'
$dbTestCredential = Get-Credential -Message '测试 MySQL 实例'
$env:DB_TEST_USER = $dbTestCredential.UserName
$env:DB_TEST_PASSWORD = $dbTestCredential.GetNetworkCredential().Password
```

### 2.2 两条现场链路

```powershell
python -B -m unittest discover -s tests -p "test_workflows.py" `
    -k concurrent_last_seat -k grades_visibility -v
```

预期出现两个用例名称并以 `OK` 结束。用例会对业务结果作断言，验收可对照下表和[实际复验日志](evidence/stage4-acceptance.txt)。

*表 1　现场用例的输入与判定条件*

| 用例 | 输入或操作 | 通过条件 |
|---|---|---|
| 争抢最后一个名额 | 准备 1 个剩余名额，12 个独立连接同时请求选课 | 1 个连接成功、11 个收到满员结果。选课计数、有效选课记录、选课日志各为 1 |
| 成绩发布与更正 | 教师提交登记单，管理员退回或发布。发布后提交两份同版本更正申请 | 发布前本人不可见。样例成绩发布后为 87.00，更正为 97.00 并记录前后值。过期版本的申请被拒绝 |

需要核对全部核心场景时，移除 `-k` 参数运行完整用例。终期复验已在独立 MySQL 8.0.45 实例导入两份 SQL，核对 63 张 InnoDB 基表、3 个视图、103 个外键、59 个 CHECK 约束和新增索引的列顺序。**15 个完整回归场景和 2 个定向演示用例均通过。** [终期复验日志](evidence/stage4-acceptance.txt)

### 2.3 优化演示

现场先展示[第三阶段执行计划与原始测量](evidence/stage3-benchmark.txt)。查看不限申请类型的待办首页，优化前索引节点读取 24,000 行并出现排序，优化后按新索引读取 50 行。两次输出内容和顺序逐项一致。

需要现场重跑时，使用支持 `EXPLAIN ANALYZE` 的 MySQL 8.0.18 或以上版本。数据生成和基准执行需要额外时间，可以后台准备，汇报时先看已保存的执行计划。

```powershell
python -B tests/benchmark.py --rows 120000 --repeats 30
```

优化汇报引用第三阶段的测量日志。索引前后在同一测试实例、同一份 120,000 条合成申请上执行。每次基准的墙钟时间会随运行环境变化，现场核对重点是索引选择、排序节点、读取行数与结果一致性。如果现场数据库无法连接，可打开已保存的复验日志和基准日志继续讲解。演示结束后清除会话中设置的密码变量。

```powershell
Remove-Item Env:DB_TEST_PASSWORD
```

## 3. 答辩问答备查

- **为什么要分开课程和教学班？** 课程保留名称、课程性质等目录信息，教学班描述某学期的具体开课，包含容量、上课班号和授课关系。选课记录把学生与具体教学班关联，同一课程可以跨学期开多个班。
- **防止超选靠哪一层？** 教学班容量用带条件的更新控制。SQL 只在 `enrolled_count < capacity` 时增加计数，选课记录和日志与计数同事务提交。学生行锁解决同一学生同时请求造成的冲突、重复与学分超限。
- **为什么成绩要分登记单和分项？** 发布状态由登记单控制，可以整班审核。分项记录支持权重计算和审计。单条已发布成绩修改时，应核对更正申请中的版本并记录前后快照。
- **为什么旧待办索引排序时仍要读很多行？** `request_type` 位于状态和提交时间之间，旧索引的时间顺序在每种申请类型内部成立。不限定类型时，新增索引让所有待审记录按提交时间和申请编号整体有序。
- **实测结果能说明什么？** 回归证明本地 MySQL 中的表结构、约束和测试用业务事务满足已覆盖场景。待办基准验证特定查询与合成数据下的读路径变化。校方正式接口、真实负载和现场部署需要另行验证。
